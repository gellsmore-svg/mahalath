# Architecture Decisions

Last updated: 2026-06-13

An **Architecture Decision Record** (the `ADR-NNN` rows below) is one
design decision and the reasoning behind it. The `ADR` prefix is kept
only as a stable ID stamped on each decision and referenced elsewhere;
the term is spelled out here so the abbreviation never has to be known
cold. Records are append-only — if a decision is reversed, add a new one
rather than editing the old, and note the supersession in both entries.

## Accepted Decisions

| ID | Decision | Rationale |
|---|---|---|
| ADR-001 | Use Python 3.11+ for core orchestration. | Best fit for local LLM tooling, MongoDB, and the multi-agent debate loop. Matches the operator's existing stack and matches Tirzah's choice. |
| ADR-002 | Use MongoDB as primary storage. | Flexible document shape suits the hybrid flat dictionary + hierarchical taxonomy required by §3.1. Same local instance Tirzah already uses; logical separation via a distinct database name. |
| ADR-003 | Avoid a dedicated graph database. | MongoDB adjacency-list patterns are sufficient for the ontology graph at the foreseeable scale (vocabulary, not corpus). Matches Tirzah ADR-003. |
| ADR-004 | All LLM calls behind an agent adapter. | Allows the local model stack to evolve (Gemma, Qwen, Mistral, future European variants) without rewriting the debate loop. Matches Tirzah ADR-004; lifted verbatim because it is load-bearing. |
| ADR-005 | Use Ollama as the initial local model runtime. | The operator already has Ollama configured for Tirzah. Avoid a second runtime install at bootstrap time. `llama-cpp-python` remains an optional future adapter. |
| ADR-006 | Hybrid flat + tree ontology layout. | Required by §3.1: flat dictionary for O(1) label lookup, hierarchical taxonomy for navigation and inheritance. Both views point at the same underlying entry records. |
| ADR-007 | Hierarchical numeric labels for ontology entries. | The operator-recommended `MPL-001.000.001a` format in §3.1 is the default. Format is enforceable per ADR-008. |
| ADR-008 | Label format and assignment is an agent decision, not a code constant. | §3.1 requires agents to decide label format. The format is recorded per ontology version and enforced by validation rather than hardcoded. |
| ADR-009 | Maximum 50 agent debate iterations per term before escalation. | Raised from §3.2's draft default of 25 after the 2026-06-06 Stage 1.7 live smoke showed gemma3:1b takes 22–23 iterations to clear the 8.0 threshold on plain technical nouns — leaving almost no headroom for harder terms. Still configurable in `config.yaml`. With gemma4:e2b (current default) most terms converge in 1–2 iterations, so the 50 cap is now safety budget, not the binding constraint. |
| ADR-018 | MPL labels are immutable once assigned. | Re-parenting changes tree edges and the denormalised `parent_label` field only; the label string itself never changes. Preserves the audit-log invariant that any historical reference to an MPL label resolves to the same entity. Cost: the visual reading of "MPL-X is at depth N because it has N segments" no longer matches reality once edges are re-attached — a child of MPL-002 can carry the label MPL-003 (assigned when it was top-level). Tree edges (`ontology_tree`) are authoritative for structure; numeric segments are only a creation-time hint. |
| ADR-019 | Human labels are approximate interfaces, not the ontology itself. | The MPL identifier (`MPL-NNN[.NNN…][a-z]?`) is the load-bearing address into machine-native semantic representations. `canonical_term`, `aliases`, and human-readable strings are operator-facing affordances that ease browsing and dictation, NOT the ontology's actual content. Implications: (a) the chat surface (`/api/chat`) treats natural language as input to a resolution step that returns MPL identifiers — the model is asked to cite MPL labels in its prose, not term names; (b) a single `canonical_term` can host multiple distinct meaning-vectors keyed by `context_id` (a `DefinitionContext` per ADR's polysemy stance) without ambiguity, because the underlying address is the (MPL, context_id) pair, not the human word; (c) glossary export shows MPL identifier as primary and the term as a secondary label, never the other way; (d) renaming a `canonical_term` is a cosmetic operation that does NOT change the entry's identity. This stance follows from the design principle "Mahalath clarifies what it means" — clarification operates on machine-native concept space, with human language as an approximate lens onto it. |
| ADR-010 | Confidence threshold 8.0 (out of 10) for accepting an outcome; below threshold goes to the undecided queue. | §3.2 default. Threshold is configurable. Confidence is on a 0.0–10.0 scale to match Tirzah's edge confidence scale. |
| ADR-011 | Watched `input/` folder for ingestion; archive to `processed/` after success. | §3.3 requirement. Matches Tirzah's watched-folder pattern; same APScheduler-style polling cadence is appropriate. |
| ADR-012 | Five runtime folders, all gitignored: `input/`, `processed/`, `ontology/`, `logs/`, `undecided/`. | §5 requirement. The folders themselves are committed (via `.gitkeep`) but their contents are not. |
| ADR-013 | Use `.restart.md` + `.session-log.md` handoff discipline. | Borrowed from Tirzah where it worked well for multi-agent coordination. `.restart.md` is canonical current state; `.session-log.md` is append-only chronological narrative. |
| ADR-014 | Mahalath remains runtime-independent of Tirzah. | The two systems share operating philosophy but serve different purposes. Coupling them at runtime would force one's evolution to drag the other. Code-reading cross-pollination is encouraged; imports across project boundaries are not. [Scoped 2026-06-13 by ADR-031: a single OPT-IN, operator-configured exception — synchronous Tirzah context-collation at ingestion — is permitted; the default and the no-integration mode keep strict independence, so Mahalath still runs standalone.] |
| ADR-015 | Source material is preserved verbatim. | Mahalath analyses source documents to extract candidate terms; it does not rewrite, summarise, or compress source. Matches Tirzah's source-preservation discipline and §3.3 of the requirements. |
| ADR-016 | Reject duplicate source files by SHA-256 checksum at ingest time. | Same content-based duplicate rejection Tirzah uses (its ADR-016). Avoids re-processing the same source under a different filename. |
| ADR-017 | Logical separation between Mahalath and Tirzah MongoDB databases. | Default database name `mahalath_dev` (configurable). Same Mongo instance; different database. Avoids any collection-name collision and lets each project evolve schemas independently. |
| ADR-020 | The retrieval layer reuses the existing schema; no parallel "retrieval node" document. | An external proposal suggested a second node shape (`codified_label`, `parent_id`, `path`, `meanings`, `variants`, opaque `mah_term_*` ids). That duplicates `ontology_entries` + `definitions` + `ontology_tree` + `definition_contexts`, which already carry every field it names. A second schema means a breaking migration and two sources of truth. Decision: retrieval is a *read view* over the current collections. The only additive schema changes permitted for retrieval are (a) a denormalised `path` (ancestor MPL labels) on `ontology_entries`, maintained on insert/reparent, and (b) an optional per-definition consensus score on `DefinitionVersion`. See `docs/retrieval-spec.md`. |
| ADR-021 | Codified labels stay opaque; retrieval never bakes semantics into the key. | The proposal's `MAH_BANK_FIN_20250610_V3` encodes domain + date + version *in the identifier*. That contradicts ADR-019 (labels are approximate interfaces, not the ontology) and ADR-018 (labels are immutable): a label that names its domain/version becomes wrong the moment a term is re-framed or re-versioned. Decision: the codified reference an LLM retrieves and cites is the MPL label (optionally the `(MPL, context_id)` pair for a specific frame). Domain lives in the tree `path` and `references_labels`; version lives in `definitions[].` order/timestamps; frame lives in `context_id`. Retrieval surfaces these as *fields* alongside the opaque label, never inside it. |
| ADR-022 | Retrieval surfaces all frames; the consuming LLM disambiguates. | For a matched human term, retrieval returns every codified meaning (one per `context_id` frame) with provenance — it does not pre-select "the" meaning, because only the caller holds the question/context that resolves the polysemy. The same API serves two consumer roles: a retrieval-LLM that pares the frame set and forwards survivors to an answer-LLM, or an answer-LLM that reasons over the full set directly. Each meaning is keyed by the `(mpl_label, context_id)` handle with `context_name` as its readable label; selection state lives with the caller, not in Mahalath (retrieval stays read-only). Resolves retrieval-spec Q1. |
| ADR-023 | Returned meanings are reference-closed. | A description written in codified terms is only interpretable if every codified term it cites is itself resolvable. So whenever an included meaning's description references other MPL labels (via `references_labels`), those entries are added to the bundle too — transitively until closed, with a visited-set cycle guard (same pattern as the staleness cascade). The closure is mandatory: token-budget pressure degrades the fidelity of deep closure nodes (compact label + active meaning instead of full provenance) but never drops a referenced term. v1 closes at entry-level reference granularity; per-frame reference tracking is a later refinement (retrieval-spec Q5). |
| ADR-024 | Intent annotates definitions; it never creates entries or enters labels. | Accepted 2026-06-11 (operator, resolving DQ-013). Inferred illocution (intent tags, intentionality, intent confidence) is stored as optional metadata on `DefinitionVersion`. It never justifies a new ontology entry, never partitions an existing entry, and never appears in an MPL label (ADR-021). Contradistinct splits remain driven by meaning difference alone (DQ-005). Prevents multiplicative ontology growth (frames × intents) and keeps the §4 neutrality NFR intact — intent is deployment metadata about the source, not semantics of the term. Full evaluation: `docs/intent-extension-evaluation.md`. |
| ADR-025 | Intent attribution uses ordinal intentionality and a separate intent confidence, both consensus-gated. | Accepted 2026-06-11 (operator, resolving DQ-013/DQ-014). `intentionality` is `low \| medium \| high` (never a float score); `intent_confidence` is on the standard 0–10 scale and is distinct from definitional confidence and from any future effectiveness measure (perlocution; out of scope). Model-sourced intent tags are stored only on multi-pass unanimity (S2.5 machinery); below-threshold attributions route to operator review. The I-D evaluation gate (unanimity rate on a real corpus run) is the go/no-go criterion for model-sourced attribution; operator-authored tags are safe regardless. Local models cannot support float-precision intent scores (S2.4 direction-variance evidence); a wrong-but-stored intent is worse than an absent one. |
| ADR-026 | Utterance-level semantic instances are out of Mahalath's scope. | Accepted 2026-06-11 (operator, resolving DQ-013). The intent-extension proposal's `semantic_instance` document (locution span + context + illocution per utterance) is passage/memory-shaped work and belongs to Tirzah if anywhere (ADR-014). Mahalath absorbs the concept-level residue only: per-definition intent annotation and (optionally) `source_quotes` locution anchoring on entries. |
| ADR-027 | Decision-effectiveness self-analysis is a read-only derived view; periodic snapshots are file-based, not a tenth collection. | Accepted 2026-06-12 (build-time, S2.39, closing requirements §3.4 "periodic self-analysis of decision-making effectiveness"). `analysis.py` computes the report by aggregating the existing audit collections (`decision_log`, `action_proposals` incl. operator verdicts, `undecided_queue`, `ontology_reviews`, `ontology_entries`) at read time — the analysis layer gets no Mongo write path, so analysing decisions can never mutate them. The headline metric is calibration: operator accept/reject verdicts bucketed by the agent confidence stated at proposal time. The "periodic" half (REM nightly tail + `effectiveness --snapshot`) appends one JSON line to `logs/effectiveness.jsonl`, following the per-document process-log precedent (ADR-012 folders): trend data accrues without a schema change, stays greppable, and is trivially erasable. Revisit a Mongo-backed snapshot store only if the operator wants in-DB trend queries. |
| ADR-028 | Multilingual support is discrete language lexicons as peers; no language is privileged and no canonical concept layer exists. | Accepted 2026-06-12 (operator, inline CLI discussion of the multilingual proposal). Each language's lexicon is built from its own evidence with its own tree; English is merely the first lexicon ingested. An MPL label addresses a meaning within one lexicon — the consuming citation is (language, label, frame), and the earlier "language-independent machine-native concept" framing is corrected accordingly. The proposal's Layer-2 "canonical semantic concepts" is NOT adopted: the stated purposes (translation creation/review via weighted mappings; cross-language illocution comparison) are fully served by pairwise mappings. A hub node may only ever be *promoted from* an accepted mapping clique if the data demands it — never created by ingestion or model initiative. Locale (country) is a plain attribute on definitions (evidence provenance, optional retrieval filter); it never creates structure — the proposal's variance-triggered branching clause is rejected. |
| ADR-029 | Cross-language mappings are first-class debated objects under the standard confidence constitution; alignment is never performed at ingestion. | Accepted 2026-06-12 (operator). A mapping is a semantic assertion between two lexicon entries: governed relationship taxonomy (equivalent / partial_overlap / narrower_than / …, a managed vocabulary like frames and intents), 0–10 confidence, N-pass attribution gated on the MAJORITY verdict — none included — with confidence = median across typed votes, promotion at the standard threshold, no-majority/under-threshold stored as unresolved (the undecided-queue pattern). [Amended 2026-06-12 (operator), relaxed from strict unanimity + min() after the first live de→en dry-run: families kept unanimously asserting relatedness while splitting partial_overlap vs narrower_than, and min() was hostage to one family's scale skew (the S2.42 pathology); a majority of none-votes now rejects, so a lone scout-model dissent cannot park junk pairs as unresolved. Minority votes are preserved verbatim in per_pass.] Mappings carry provenance + debate transcript + status lifecycle and participate in the staleness cascade (redefining either endpoint flags the mapping for re-audit). Generation happens in REM-style background consolidation, never during ingestion (deferred alignment prevents semantic contamination). Mapping output includes illocution-profile comparison of the endpoints — deployment divergence is translation-risk signal in its own right, computable because intent is attributed per-lexicon before any mapping exists. Empirical gate before model-sourced mappings are kept (the I-D pattern); embeddings-based candidate pruning (S-E) is a near-prerequisite at scale. |
| ADR-030 | One collection, global opaque label sequence, language as a field; retrieval never interleaves local and mapped results. | Accepted 2026-06-12 (operator). Entries gain an entry-level `language`; existing data backfills as "en". Labels stay one global opaque sequence (a label never reveals its language — ADR-021 extended). Single collection: compound (language, term) indexes match split-collection performance at vocabulary scale; Mongo's one-text-index limit plus per-document language stemming favours it; CJK needs the embeddings path. Splitting later is a filtered copy on the language key. Retrieval: query language is an explicit parameter (detection only as fallback); cross-language expansion is opt-in, depth-1 (no silent transitive composition); mapped results return in a separate labelled section carrying relationship/confidence/rationale — local and mapped scores are never blended (the ADR-022 "caller disambiguates" contract extended across languages). |
| ADR-031 | Tirzah context-collation is an optional, operator-configured, synchronous ingestion-time integration; opt-in only, scoping ADR-014. | Accepted (design) 2026-06-13 (operator); implementation deferred to v2. PURPOSE: raise the QUALITY of the context a debate sees by collating a candidate term's whole-document context before it is defined — calibrate the input so the lossy quantized-model "compression" yields a better definition. This is a DISTINCT capability from the local meaning-embedding/"fingerprint" work (which serves cross-language candidate shortlisting in M-C): embeddings find similar pieces; Tirzah collates them into a higher-fidelity, document-specific context. SHAPE: a synchronous request from Mahalath to Tirzah during ingestion (operator chose a live request over an offline hand-off), selected by a Mahalath config setting with three modes trading performance against quality — (a) `none`: no Tirzah, current local-section behaviour, fastest, preserves strict ADR-014 independence; (b) `fast`: a plain request for mechanical similarity retrieval, no model in Tirzah's loop; (c) `llm_brokered`: Tirzah uses a model to synthesise/compile the chunks, best quality, slowest. Modes (b)/(c) are the scoped runtime dependency on Tirzah that ADR-014 otherwise forbids; (a) and "feature off" keep Mahalath standalone. CONSTRAINTS for the build: define ingestion's fallback when Tirzah is unavailable or times out (degrade to `none`, retry, or fail the document — undecided); mode (c) stacks another local-LLM call into the ingestion path and is slow on current hardware (the ≥600s Ollama-timeout reality); the integration fixes definition ACCURACY (faithfulness to the document), not FLUENCY (grammar slips need the debate self-check, a separate lever). OPEN: the request contract depends on what Tirzah exposes (a queryable store vs a "document + term → collated context" call) — to be settled before implementation. |
| ADR-032 | Optional `hoglah` adapter: route generation AND embeddings through a Hoglah queue daemon instead of calling Ollama directly. | Accepted + implemented 2026-06-13 (operator). PURPOSE: for a walk-away run, serialize every model call through one durable local queue (Hoglah, concurrency default 1) so a single constrained GPU is not thrashed, with persistence/timeout enforcement across restarts. TOPOLOGY: a SEPARATE `hoglah run` worker daemon executes jobs off a shared SQLite queue and writes results to an output folder; Mahalath is a PURE SUBMITTER (`hoglah` client constructed `start_worker=False` — Hoglah ADR-016 ensures it never recovers/clobbers the daemon's in-flight jobs). Selected per channel via `model_adapter` / `embedding_adapter` / `chat_adapter = "hoglah"`; settings under `runtime.hoglah`. Keeps the existing synchronous `generate()`/`embed()` Adapter contract — the adapter submits then blocks on the result — so NO pipeline rework and other adapters are untouched. FINGERPRINTING: embeddings route through Hoglah's embedding jobs (ADR-013 there); the adapter maps Hoglah's non-finite-vector failure back to `EmbeddingNaNError` so existing NaN-resilience still applies. DELIVERY (config `delivery`): "poll" the output folder, or "callback" — Mahalath runs a tiny stdlib HTTP receiver and passes its OWN URL (`callback_host`/`callback_port`, port 0 = ephemeral) to Hoglah per job (nothing Mahalath-specific is baked into Hoglah; ADR-015 there is generic), with the output folder as automatic fallback if a push is missed. `hoglah` is an optional dependency (`pip install 'mahalath[hoglah]'`); the other adapters need it not installed. DISTINCT from ADR-031 (Tirzah, context QUALITY): this is an execution-transport choice, not a context-collation capability. |

## Notes On Decision Reuse From Tirzah

Several decisions above lift directly from Tirzah's architecture-decisions
doc (ADR-001 through ADR-004, ADR-013, ADR-015, ADR-016). This is
intentional. Where the operating philosophy is shared and the two systems
both run locally on the same hardware against the same MongoDB instance,
reusing the proven decision saves design effort and gives contributors
a stable shared vocabulary. Any decision lifted from Tirzah is named
explicitly so future divergence is visible.
