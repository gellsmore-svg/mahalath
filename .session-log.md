## 2026-06-06 [claude] — Stage 1 end-to-end landed

Bootstrap commit `fe0cacc Bootstrap project scaffolding` was pushed to
`origin/main` earlier in the day. After operator approval to "continue
with Mahalath as single focus and start making the product once what
you need is in place", Stage 1 was built in seven chunks:

- **S1.1 db package + labels.** `labels.py` (MPL label parse / format /
  successor helpers, 22 unit tests), `db/{client,models,indexes,
  repositories}.py`. Six collections with indexes including unique
  constraints on `documents.checksum_sha256` and on
  `(ontology_tree.parent_label, child_label)`. Live MongoDB round-trip
  proved all six collections accept inserts and reject duplicate
  checksums.
- **S1.2 adapter package.** `Adapter` protocol, `MockAdapter` (deduped
  prompt-substring matching with `Speaker:` tags), `OllamaCliAdapter`
  (subprocess to Windows Ollama binary, modern `--think=false
  --hidethinking` flags with legacy fallback, `--format json` support).
  Live smoke against gemma3:1b: plain prompt 4.9 s, JSON prompt 1.0 s,
  JSON parses cleanly.
- **S1.3 ingestion.** `ingest_one` reads bytes, SHA-256, dedupes,
  archives to `processed/`, verifies checksum post-copy, writes
  `DocumentRecord`, emits `logs/ingest-<id>.md`. CLI command
  `mahalath ingest-one <path>` wired. Live CLI smoke: clean ingest,
  duplicate detection, exit code 0 + JSON output in both cases.
- **S1.4 candidate term extraction.** `extract_candidate_terms` builds
  a JSON-format extraction prompt and parses the response. Live test
  on the agonist intro returned 10 candidates of which 8 were correct
  and 2 were prompt-leak ("multi-word phrase", "technical noun"). Added
  a "term must appear in document" filter as a defensive measure;
  re-run produced 8 clean candidates in 2.4 s.
- **S1.5 debate loop.** Pure (no MongoDB) `run_debate` taking term +
  context + document_id + adapter + runtime config. PrecisionCritic
  speaks first per iteration, then SynthesisExplorer sees the critic's
  turn; aggregate confidence = `min(pc, se)` per DQ-003. Accepts at
  threshold, returns undecided at iteration cap. Live test on
  "agonist" via gemma3:1b: accepted in 2 iterations at confidence 8.0
  in 5.6 s. **First snag**: initial MockAdapter substring matching was
  ambiguous because both preambles share the word "PrecisionCritic";
  fixed by adding `[Speaker: precision_critic]` / `[Speaker:
  synthesis_explorer]` literal tags exposed as public constants.
- **S1.6 ontology persistence.** `persist_debate_result`: MPL label
  assignment (top-level by default; child under parent if given), write
  ontology entry + optional tree edge + decision log + every agent
  exchange + undecided queue routing as appropriate. Five live MongoDB
  tests cover the accepted/undecided/parent-child paths.
- **S1.7 end-to-end wiring.** `mahalath process-document <id> [--max-
  terms N]` and `mahalath list-ontology`. Live end-to-end run on the
  agonist intro: ingested in ms, debated 2 terms in 1m58s ("agonist"
  → MPL-001 @ 8.0 after 23 iterations, "receptor" → MPL-002 @ 8.0
  after 22 iterations). Mongo state at end: 1 document, 2 ontology
  entries, 2 decision_log entries, 90 agent_exchanges, 0 undecided,
  0 tree edges. Activity log emitted to `logs/process-*.md`. Both
  definitions are domain-correct.

**Tests: 73 passing.**

**Observations to feed into Stage 2 prioritisation:**

- gemma3:1b takes ≈ 22 iterations to clear the 8.0 threshold on plain
  technical nouns — ≈ 1 minute per term. For a real corpus this is the
  binding constraint. Options: stronger model (gemma4:e2b is pulled
  locally), prompt tuning to ratchet confidence faster, or temporary
  threshold drop.
- Stage 1 only produces top-level labels. Hierarchy / contradistinct
  splits are schema-ready but unexercised. Stage 2 needs an explicit
  decision on how parent assignment is decided (operator-tagged?
  second-pass debate? structural co-mention analysis?).
- The defensive "term must appear in document" filter on extraction
  catches the gemma3:1b prompt-leak failure mode reliably; worth
  keeping even with stronger models.

iterations to a higher value to suit as you see fit"). Smoke data
justified this: agonist needed 23/25 and receptor needed 22/25, so the
old cap was at the edge of what gemma3:1b can deliver on the easy

harder terms have room to converge before escalation. ADR-009 updated

## 2026-06-06 [claude] — first real corpus run (rs-cbo-beginner-v1.md)

Operator said "you decide". Chose Stage 2 item #5 (first real corpus
run) as the highest-information move — every other Stage 2 task
benefits from knowing what the pipeline produces on real source.

Picked `~/RS-claude/rs-cbo-beginner-v1.md` (46 KB / 45,913 chars,
beginner edition of the operator's Coherent Biblical Ontology book).
Smallest book-edition file in the corpus; high concept density per
page; just under the 50 KB extraction char budget. Ingested into
`mahalath_dev` (the project's primary DB).

**First attempt failed**: extraction returned
`{"text": "The response is not provided..."}` in 3.6 s — gemma4:e2b
gave up because the prompt was 46K characters with instructions
leading. Diagnosed by bisecting on document length:

| chars  | result                                              |
|--------|-----------------------------------------------------|
| 3-30K  | works, real candidates                              |
| 35-42K | model engages but summarises the book instead of extracting (theology essays, chapter outlines) |
| 46K    | model returns "no text provided" boilerplate        |

Root cause: instructions too far from the model's recency window. Fixed
by:

- **Inverting prompt order**: document FIRST, instructions LAST. Model's
  last context is "what to do", not "what to read".
- **Tighter rules**: explicit "single noun phrase, not a sentence or
  fragment" rule kills the failure where the model treated each item in
  a list as a separate candidate ("Something travels", "Something gets
  rearranged" etc.).
- **DEFAULT_CHAR_BUDGET lowered to 30K**: largest safe single-shot
  budget on gemma4:e2b until proper chunking lands.

Re-run produced **5 ontology entries in 58.8 s**, all real RS
terminology, all accepted in 1-2 iterations:

- MPL-001 **Ontology** conf 8.0 — generic philosophy-dictionary
  definition; doesn't capture the book's "what something really is"
  framing. Style-alignment issue (agents don't know the covenant-neutral
  / scripture-authoritative voice).
- MPL-002 **Relational Substrate** conf 8.5 — "fundamental reality of
  interconnectedness". Captures it.
- MPL-003 **Substrate** conf 8.0 — near-duplicate of MPL-002. **This is
  the hierarchy-emergence problem the schema was designed for and Stage
  2 must solve.** They should be parent/child, not siblings.
- MPL-004 **Continuity** conf 8.0 — accurate.
- MPL-005 **Vortons** conf 8.5 — "stable topological knots within the
  structure of the world's weave". Specific and correct.

**Stage 2 signals strengthened by this run:**

1. **Heading-aware chunking is mandatory.** A 30K budget on a 46K
   beginner book misses the last third entirely. The bachelor edition
   is 270 KB; nothing will work for it without chunking.
2. **Hierarchy emergence is the next product-shaping decision.** The
   MPL-002/003 near-duplicate is a real defect that the existing
   schema can fix once we know HOW agents propose parent edges.
3. **Style-prompt overlay is needed.** Generic-philosophy definitions
   for a covenant-neutral biblical-ontology source are a clear miss.
   Could be solved with per-corpus system prompt seeded with the
   author's voice notes.

**Changes:** `src/mahalath/extraction.py` (prompt structure + char
budget + stricter rules). Tests still 73/73. Ontology entries persist
in `mahalath_dev`.

**Next action:** wait for operator direction. Hierarchy emergence is

## 2026-06-06 [claude] — Stage 2: agent-callable actions + hierarchy review

Operator framed the design: "you as an LLM figured this out, so we let
the local LLM figure it out and give it a python interface to make it
happen." Built it in three sub-slices.

**S2.1 — actions + dispatcher + audit.** Four action types
(propose_parent / propose_alias / propose_merge / propose_split) as
frozen dataclasses; JSON parser; validator (checks existence, cycles,
canonical-term collisions, variant-as-parent block, alias duplicates);
applier (writes tree edge + denormalised parent_label for parent;
$addToSet for alias); dispatcher with auto-apply at confidence
threshold; destructive actions always route to pending_review
regardless of confidence. New `action_proposals` collection records
every proposal regardless of outcome (applied / pending_review /
invalid). ADR-018 added: **MPL labels immutable once assigned**; tree
edges are authoritative, label string is a stable identifier.

**S2.2 — hierarchy review module.** `run_hierarchy_review(focus_label,
db, adapter, runtime)`: snapshot existing entries, build curator
prompt showing each entry's MPL label + canonical term + short
definition + current parent, ask gemma4:e2b for structural actions,
parse JSON into Action records, persist an `OntologyReview` row with
full prompt+response (audit trail). Decoupled from dispatcher so
caller controls thresholds and routing.

**S2.3 — wire to process-document + live smoke.** Post-accept review
runs on every accepted entry. `mahalath process-document <id>` now
emits a `hierarchy_review` block per term in the JSON output and in
the activity log Markdown. `--no-hierarchy-review` flag opts out.

**Two live smokes.**

*Focused* (against the existing 5-entry ontology in mahalath_dev,
hierarchy review on MPL-003 Substrate): first run identified the
Substrate / Relational Substrate relationship at confidence 8.0 with
the correct direction (RS child of Substrate). But the model referred
to entries by canonical term ("Relational Substrate") instead of MPL
identifier — validator rightly rejected as invalid. Prompt was
sharpened with an explicit "labels must be MPL-NNN, never canonical
term" rule + a concrete example. Re-run with sharper prompt produced
MPL identifiers correctly but with confidence 6.0 (reversed direction)
— routed to pending_review with full audit, exactly the safety design
working as intended. Model uncertainty about *direction* faithfully
reflected in lower confidence.

*Clean run* (mahalath_dev dropped, re-ingest rs-cbo-beginner-v1.md,
process-document --max-terms 5 with hierarchy review enabled): 5
ontology entries built in 1m41s, 6 action proposals across 5 reviews:

  1 applied — MPL-003 (Relational Substrate) → child of MPL-001
    (Ontology), conf 8.0. **Borderline-wrong**: model's reasoning was
    "RS is a fundamental ground upon which ontology is based" which
    actually supports the opposite direction. 8.0 was exactly at the
    threshold; this is the kind of case to watch.

  3 pending_review — confidence below 8.0 threshold. Includes the
    obvious "substrate → child of Ontology" at conf 6.0 which the
    model correctly hedged on.

  2 invalid — one used canonical term despite the sharper prompt
    (single-entry ontology edge case at MPL-001), one was the
    re-parenting attempt that *would have correctly fixed the
    relationship* (see below).

**The big find**: when reviewing MPL-004 substrate, gemma4:e2b
independently proposed `propose_parent(child=MPL-003 [Relational
Substrate], parent=MPL-004 [substrate])` at **confidence 8.5**,
reasoning: *"The 'Relational Substrate' seems to be a specific
instantiation or description of the more general 'substrate'."* This
is the exact relationship visible from reading the definitions. But
S2.1's "re-parenting not supported in this slice" rule blocked it
because MPL-003 had already been auto-applied as a child of MPL-001 in
the previous iteration. The model's capability is sound; my own
conservative design choice prevented the right action from landing.

**Audit footprint of one process-document run with hierarchy review:**

  agent_exchanges:   18  (5 debates × ~2 iterations × 2 agents)
  action_proposals:   6
  ontology_reviews:   5
  decision_log:       5
  ontology_entries:   5
  ontology_tree:      1  (the one applied parent edge)
  documents:          1

Every model interaction is queryable.

**Stage 2.4 candidates surfaced by this run** (decision pending):

  1. **Allow re-parenting at high confidence** — would have let the
     correct substrate parent land. Risk: model can reshuffle the tree
     on every iteration, churn.
  2. **Raise auto-apply threshold for parent actions** — 8.0 let the
     borderline-wrong MPL-003 → MPL-001 land. 8.5 would have routed it
     to pending_review where the operator could reject and let the
     correct 8.5 substrate proposal succeed.
  3. **Roll-back / override CLI** — `mahalath reject-proposal <id>`,
     `mahalath rollback-action <proposal_id>`. The audit trail makes
     this safe.
  4. **Multi-pass consensus** — run hierarchy review N times,
     dispatch only if all N agree. Cost goes up; variance goes down.
  5. **Canonical-term resolution** — accept canonical term in action
     fields and resolve to MPL automatically. Robust to model drift.

## 2026-06-06 [claude] — Stage 2.4: re-parenting unblocked

Operator said "you decide and continue". Picked option 1 (allow
re-parenting at high confidence) because it directly addresses what
S2.3 surfaced: the model proposed the correct substrate parent at
conf 8.5 but S2.1's first-slice rule blocked it.

Changes:

- `actions._validate_parent`: removed the "child already has parent"
  hard rejection; added a same-parent no-op detection so a proposal
  that wouldn't change anything is rejected cleanly with status
  invalid rather than silently applied.
- `actions._apply_parent`: detects re-parenting (child has a different
  parent now), deletes the old tree edge first, then writes the new
  edge and updates `parent_label`. The application_result records
  `previous_parent_label` and `reparenting: True` so later operator
  rollback is straightforward.
- `actions.dispatch`: now picks the effective threshold based on
  whether the action is re-parenting. Initial parent assignment still
  uses `auto_apply_threshold` (8.0 default); re-parenting requires
  `reparent_threshold` (8.5 default). Both configurable per call.
- `actions.is_reparenting(action, db)`: small public helper so the
  CLI / future audit tools can ask the same question.
- `hierarchy.py` task instructions updated to mention re-parenting is
  allowed at confidence ≥ 8.5.
- Tests: removed the "rejects_already_parented" test (logic inverted).
  Added: allows_reparenting, rejects_same_parent_noop, two dispatch
  tests for the new thresholds (above/below), one ensuring initial
  parent still uses the lower threshold.

Tests: 100 → 104.

**Live smoke** (mahalath_dev dropped, re-ingest beginner book, process
5 terms with hierarchy review):

Final shape after the run:

  MPL-001 Ontology               (top-level)
  ├─ MPL-002 Biblical            (applied conf 8.0)
  MPL-003 Relational Substrate   (top-level)
  ├─ MPL-004 Substrate           (applied conf 8.0)  ← see below
  MPL-005 Continuity             (top-level)

5 action proposals, 2 applied, 1 pending_review, 2 invalid.

**The direction-variance problem becomes the headline.** In the S2.3
run gemma4:e2b proposed Relational Substrate → child of Substrate at
conf 8.5 (correct direction by my reading of the book). In this S2.4
run, with re-parenting machinery in place, the model proposed the
*opposite* direction — Substrate → child of Relational Substrate — at
conf 8.0 (auto-applied as initial assignment because MPL-004 was
freshly created without a prior parent).

The model is confident a relationship EXISTS between Substrate and
Relational Substrate but inconsistent about WHICH IS THE PARENT. The
confidence score conflates "there's a relationship" with "direction
X→Y is correct". Higher thresholds don't fix this; the model passes
8.0+ in both directions.

Re-parenting itself wasn't exercised by the live model (it was
exercised by the no-op detection when MPL-005's review re-proposed
the already-applied MPL-004 → MPL-003 edge — caught and recorded as
invalid). Unit tests cover the apply path.

**Stage 2.5 options surfaced by this** (decision pending):

  1. **Multi-pass consensus on direction.** Run hierarchy review N=3
     times; only auto-apply if all three agree on (child, parent).
     Costs ~3× per accepted entry; kills direction variance.
  2. **Dedicated direction debate.** Treat direction as a debate
     between two agents: one defends X→Y, one defends Y→X, min
     confidence wins. Same machinery as Stage 1 debate.
  3. **Lower auto-apply threshold + larger operator queue.** Route
     all parent proposals to pending_review by default; operator
     accepts or rejects from a CLI tool. Less autonomy, more
     correctness.
  4. **Definition-first refinement.** The root cause is two
     near-identical definitions (Substrate ≈ Relational Substrate).
     Re-debate the definitions when the hierarchy reviewer flags them
     as ambiguously related. Treats the symptom at its source.

Recommend option 1 (multi-pass) as the simplest direct fix; option 4
as the principled fix.

## 2026-06-06 [claude] — Stage 2.5: multi-pass consensus on direction

Operator said "you decide and continue". Picked S2.5 option 1
(multi-pass consensus) — simplest direct fix for the direction-variance
problem surfaced in S2.4's live run.

Added `hierarchy_consensus_passes: int = 3` to RuntimeConfig. New
`run_hierarchy_review_consensus` runs the single-pass review N times,
persists each pass as its own OntologyReview row (full audit), and
aggregates actions by strict unanimity. Action identity is
(action_type, sorted-payload-pairs) so two parent proposals with
swapped child/parent labels are distinct keys and cannot accidentally
aggregate — exactly the property direction variance needs. Consensus
confidence = min across passes (matches Stage 1 DQ-003).

CLI now uses the consensus path by default; `--consensus-passes N`
overrides for ad-hoc runs. Per-pass diagnostics surface in both the
JSON output and the activity log Markdown, so when consensus fails the
operator can see exactly what each pass proposed.

Tests: 104 → 110. New SequentialMockAdapter helper returns a different
canned response per call. Six new tests cover all-agree passthrough,
min-confidence aggregation, single-disagreement drops, direction-flip
across passes (the headline disagreement case), n=1 passthrough,
per-pass review persistence.

**Live re-run** (mahalath_dev dropped, beginner book, 5 terms,
consensus=3, 2m14s — 33% overhead vs single-pass):

  MPL-001 Ontology              — 0/3 unanimous; nonsense self-loop proposals dropped
  MPL-002 Biblical              — 3/3 agreed parent=MPL-001 conf min 6.0 → pending_review
  MPL-003 Coherent Biblical Ontology — 3/3 agreed parent=MPL-001 conf min 8.0 → APPLIED
  MPL-004 substrate             — 3/3 agreed parent=MPL-001 conf min 6.0 → pending_review

The last result is the headline. With single-pass (S2.4 run),

Zero wrong-direction auto-applies in this run, vs one in the S2.4

## 2026-06-11 [claude] — S2.31: retrieval S-B (materialised paths + subtree)

denormalised field with proper maintenance, plus the `subtree` read view.

**New `paths.py`** — the path-maintenance layer:
- `compute_path(db, label)` — the canonical derivation (walk
  `parent_label` root-first, cycle-safe, bounded depth).
- `resolved_path(db, entry)` — prefers the stored `path`; falls back to a

- `backfill_paths(db)` — one-shot idempotent migration (mirrors
